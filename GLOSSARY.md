# Kouen Domain Language

## MCP Surface

| Term | Definition | Aliases to avoid |
|------|-----------|-----------------|
| **Task** | A session-scoped checklist item, persisted per-session, MCP-addressable (create/list/update/delete via `kouen-mcp`). Belongs to exactly one session — not a global, session-independent object. | Superset Task (different model — theirs is global, not session-scoped), Todo |
| **Task Dashboard** | UI view aggregating Tasks across all sessions into one place, for the human user (not an MCP-exposed object itself). | Fleet dashboard (that's agent/notification status, a separate existing concept) |
| **Worktree (MCP resource)** | The existing worktree-per-branch-per-agent isolation (`WorktreeManager`), newly exposed as an MCP-addressable CRUD resource (`kouen-mcp` tools to create/list/delete). The underlying git-worktree mechanism is unchanged — this term refers specifically to its new external-agent-facing surface. | **Workspace** — already a distinct, pre-existing Kouen term (`WorkspaceID` in `SessionEditor.swift`, a window-level container of sessions). Do not reuse "Workspace" for the worktree concept — that's the naming Superset uses, not Kouen's. |
| **Host (MCP resource)** | An entry in the existing `RemoteHostStore` (SSH remote machine config), newly exposed read-only via `kouen-mcp` (`hosts_list`-equivalent). No new storage — this term refers to the new MCP-facing view of existing state. | Remote Host (UI-facing term in `SettingsRemoteView`, same underlying data) |
| **Shader Preset** | A pre-built, Kouen-authored GPU visual effect (e.g. CRT/scanline/bloom) the user toggles on/off in Settings. Not user-authored/arbitrary shader code — that's explicitly out of scope. | Custom shader (implies user-authored code, which this is not) |
| **Automation** | A scheduled agent launch (`repoPath` + `agent` + `prompt` + `intervalMinutes`), MCP-addressable (create/list/get/update/delete/pause/resume/run-now via `kouen-mcp`). On fire, spawns a session and types `prompt` into the launched agent — same mechanism a human or `kouenSpawnAgent` uses. Kouen has no `agent-memory/plans` awareness; the connection is purely the `prompt` text convention (e.g. "ทำต่อ p40" relies on the launched agent's own CLAUDE.md continuation rule). | Superset Automation (theirs uses RRULE recurrence + a `run` log history; Kouen's is a simpler fixed-interval-minutes model with last-run status only) |
| **Scheduled Memory Maintenance Job** | A `launchd`-scheduled headless `claude -p` run (`~/.claude/scripts/memory-maintenance-apply.sh`), external to Kouen entirely — Kouen has no visibility into it, no MCP resource represents it, `kouen-mcp` cannot list/pause/inspect it. Scans this project's `agent-memory/` for broken `[[link]]`s and archive/crystallize candidates. | **Automation** — surface-similar ("scheduled agent launch") but a different mechanism end to end: Automation spawns a real Kouen session via `kouenSpawnAgent`; this uses `claude -p --allowedTools "Read Edit Write"` with no session/pane at all. Don't conflate — a `kouen-mcp` query will never show this job. |
| **Agent Routing Rule** | An ordered, user-configured rule (repo-path glob and/or `SignalFileRouter`-detected stack) that resolves to an `AgentKind`, evaluated only when a spawn call passes `agent: "auto"` instead of an explicit kind. First matching rule wins; falls back to the existing default-agent setting when none match. Consumed by `kouenSpawnAgent` and P41 Automations (`agent: "auto"`) — spawn-time only, never mid-session. | "Model router" (Warp's term implies per-LLM-request routing inside an owned agent runtime — not applicable; Kouen only ever selects which CLI binary to spawn, never routes an individual LLM call within an already-running agent) |
| **Design Mode** | A human-facing (not agent-facing) toggle on the browser pane: hover-highlights a DOM element, click-to-select shows its key computed styles in a popover, editing a field live-applies the style via JS (`element.style[prop] = value`) for visual preview only — never persisted, never written to a source file, lost on reload. "Copy CSS" copies the edited properties as a rule block to the clipboard; the human pastes it into their own source by hand. | cmux's "Browser Design Mode" (their scope may include more — Kouen's v1 explicitly does not do source-file diffing/round-tripping; that's a distinct, larger, unbuilt feature) |
| **Fork Conversation** | "View → Fork Conversation" splits the active pane and runs the active tab's agent CLI's own native fork command (`claude --continue --fork-session`, `codex fork --last`) in the new pane — the CLI itself branches its conversation history, Kouen never inspects or stores that history. Disabled (not shown as available) for any `AgentKind` without a verified CLI-native fork mechanism. | A Kouen-owned "conversation fork" (Kouen doesn't own agent conversation state at all — it wraps opaque CLI subprocesses; this only works because Claude Code/Codex each ship their own fork flag) |
| **Saved Layout** | A named, human-saved `PaneLayoutShape` (split directions/ratios/leaf positions only, no running processes/cwd) via "Save Current Layout as Template…" / "Apply Saved Layout…". Applying creates a new tab with fresh empty shells matching the shape. | **Layout Template** — already a distinct, pre-existing Kouen term (`KouenCore/Layouts/LayoutTemplate.swift`, the tmux-style `even-horizontal`/`main-vertical`/`tiled` built-in algorithmic layouts applied via `SessionEditor.applyLayout`). Do not reuse that name for this human-saved-custom-arrangement concept — different mechanism, different data shape, caught before it collided. Also distinct from daemon **session-restore** (snapshots one specific session's live state, not a reusable template). |
| **Risky Command Advisory** | Local heuristic (`RiskyCommandClassifier`, regex blocklist) flags a just-finished shell command in an agent-active pane with a warning Toast. Fires on OSC 133 `D` (command already finished) — advisory only, never blocks or holds anything. | iTerm2's actual "AI safety-check" (a second LLM call judging each command against the original user request, holding risky ones for approval *before* they run) — that needs PTY-input interception before Enter reaches the shell, which this session didn't have time to build/verify safely. This is a smaller, honest slice: after-the-fact awareness, not prevention. |
| **Request Peer Review** | "View → Request Peer Review" finds another agent-running pane in the active tab and types a review-request prompt into it (asks the peer's own agent to run `git diff` and review). Human-triggered. | iTerm2's actual "workgroup review" (automatic on agent idle, auto-captures the peer's response and pastes it back) — the auto-trigger + response-capture + auto-paste round trip needs reliable idle-detection and cross-pane text extraction this session didn't verify against a real running agent. v1 automates only the asking step; the human reads the peer's reply themselves. |
| **Merge Waiver** | Extends the existing PR merge-strategy picker (P39 G3): normally requires `checksStatus == .pass && mergeable == true`; a PR with `reviewDecision == "APPROVED"` can merge with checks not yet green (an extra "Merge Anyway" confirmation, not silent). `mergeable` (no conflicts) is never waived regardless of approval. | Bypassing `mergeable` too — GitHub's own conflict computation is never overridden, only the checks-pass requirement |
| **Slash Command Picker** | Typing `/` at the start of a line in the Composer (⌘⇧E) shows a filtered picker (reuses `CompletionPopupView`, the same widget the file editor's completion uses) over a small fixed command list (`/clear`, `/compact`, `/model`, `/agents`, `/continue`, `/resume`, `/help`, `/cost`). Discoverability only — the commands already worked via plain passthrough to the CLI before this existed. | `@file` mention autocomplete — the other half of M9's original scope (Superset's "rich composer"), cut for this session; same `CompletionPopupView` pattern would extend to it, not built yet. Also distinct from P37 Mobile Connect's own `@`-mention/file-browser autocomplete (mobile companion app, unrelated surface, not the macOS Composer). |

## Relationships
- A **Task** belongs to exactly one session; deleting the session's underlying data does not orphan Tasks silently — behavior TBD in design (see dev-architect).
- A **Worktree (MCP resource)** maps 1:1 to a git worktree (`WorktreeManager.WorktreeInfo`); a **session** (`SessionID`) may attach to a Worktree via `SessionEditor.setWorktree`, but is a distinct runtime concept — and both are distinct from the pre-existing **Workspace** (`WorkspaceID`, a window-level container of sessions).
- A **Host (MCP resource)** is read-only via MCP — creating/editing a Host remains a Settings-UI-only action (SSH connection setup has security implications not delegated to external agents in this plan).
- An **Automation** is independent of Tasks, Worktrees, and Hosts — it does not reference any of them by ID. Its `repoPath`/`agent`/`prompt` fields are free text; if that `repoPath` happens to be a git repo with `agent-memory/plans/`, and the `prompt` happens to name a specific plan file, the *launched agent* is what reads and acts on the plan — Kouen itself never opens or parses plan files.
- A **Scheduled Memory Maintenance Job** is unrelated to an **Automation** despite both being "a scheduler fires a prompt into Claude" — no shared storage, no shared trigger path, and migrating this project's job to a real Automation (so it shows up in `kouen-mcp`, can be paused/inspected) is an open option, not yet decided (see `agent-memory/plans/memory-maintenance-rollout/design.md` in the workspace-level `~/.claude` repo).
- An **Agent Routing Rule** resolves to an existing **AgentKind** value — it picks which CLI binary a spawn targets, not which LLM model that binary uses internally (Kouen has no visibility into a spawned CLI's own model choice). It reuses `SignalFileRouter.detectProfile()`'s stack signal as one match criterion rather than duplicating stack detection.
